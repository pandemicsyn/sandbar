# @sandbar-sdk/modal (experimental)

Status: **create, exec, files, inspect, inventory, destroy and filesystem snapshots implemented; deterministic fixtures and packed Node/Bun consumers tested; live unverified**. This package uses the official `modal@0.10.1` JavaScript SDK plus a version-pinned TaskCommandRouter wire subset.

```ts
import { Sandbar, Image } from "sandbar-sdk";
import { modalAdapter } from "@sandbar-sdk/modal";

const client = await Sandbar.connect({
  adapter: modalAdapter,
  config: { appName: "my-existing-app", environment: "main", region: "us-east-1", lifecycle: { lifetimeSeconds: 300 } },
  credentials: { tokenId: process.env.MODAL_TOKEN_ID!, tokenSecret: process.env.MODAL_TOKEN_SECRET! },
});
try {
  const box = await client.sandboxes.create({
    environment: Image.prepared("im-existing-modal-image-id"), network: "blocked",
  });
  try {
    const result = await box.exec({ command: { kind: "argv", argv: ["/bin/sh", "-c", "printf ready"] } });
    await box.writeFile("/tmp/result.bin", new Uint8Array([0, 255, 129]), { overwrite: false });
    console.log(result.exitCode, await box.readFile("/tmp/result.bin"));
  }
  finally { await box.destroy(); }
} finally { await client.close(); }
```

The adapter verifies the existing Modal App and registers an owned close hook. `client.close()` releases local resources and stops Sandbar waits; it does not destroy provider compute. Modal's transport cannot guarantee cancellation of an already submitted native call.

The deployed Modal App must already exist; a prepared image ID must exist when that image path is used. `modalAdapter` looks up the App without `createIfMissing`. The server returned App ID, configured environment and official endpoint bind the native scope. The SDK does not expose a verified workspace ID, so this adapter makes no workspace identity claim. Region is explicit when configured. Custom endpoints and profile endpoint overrides fail closed. Credential strings are never placed in resource or recovery references.

Configure the default creation image with `image`: an `im-` image ID string, `{ kind: "prepared", value: "im-…" }`, or `{ kind: "oci", value: "<ref>" }`. It defaults to OCI `python:3.12-slim`, which provides the POSIX shell, coreutils and Python the adapter's features need, so `client.sandboxes.create()` works without an `environment`; a per-call environment wins. Create-time `env` is sent as the V2 create request's ephemeral secret map in the same single create call (no separate secret object); Modal applies it to the sandbox's commands, and per-call `env` overrides a name. Values never enter recovery state and are redacted from native error details. Live inheritance by exec has not been qualified. `lifecycle.lifetimeSeconds` sets the native sandbox lifetime (deprecated alias: `timeoutSeconds`), and `create({ lifecycle: { lifetimeSeconds } })` overrides it per sandbox: default 900 seconds, up to 86,400 (Modal's [24-hour limit](https://modal.com/docs/guide/sandboxes)). Modal has no renewal API.

Set `resources: { vcpus, memoryMiB }` to reserve that size: `vcpus` becomes Modal's CPU reservation (fractions allowed) and `memoryMiB` its memory reservation, sent on the single create call. Unset dimensions take Modal's defaults. Modal does not report reservations back, so the adapter records the size in a `sandbar_resources` tag and `inspect().resources` reports it only when both numbers are set. Modal rejects a size above its limits at create.

Prepared `im-` image IDs and `Image.oci("python:3.12-slim")` are supported. OCI validation in `prepare` is read-only. Inside one create submission, `fromRegistry` constructs the image, then Modal's `experimentalCreate` calls `image.build(app)` before `SandboxCreateV2`; image building may cost money. The adapter creates V2 sandboxes with `blockNetwork: true`, a unique submission name and tags, and a configured native timeout. It does not create secrets, volumes or apps. Destroy terminates compute; prepared and built images retain their existing Modal lifecycle. Image get, list and delete are unsupported (`UNSUPPORTED`): the adapter has no image inventory or standalone build, and cannot check which sandboxes still use an image before deleting it. A lost image-build response can leave a paid image with no sandbox name to observe. The adapter reports unknown and never automatically retries or claims no effect. A lost sandbox-create response is observed by native name and matching tags when the sandbox remains active. When Modal refuses a create outright, `create()` rejects with a matching error code and Modal's own reason: `INVALID_ARGUMENT`, `NOT_FOUND`, `FAILED_PRECONDITION` (as `CONFLICT`), `PERMISSION_DENIED` (as `FORBIDDEN`), `UNAUTHENTICATED` and `RESOURCE_EXHAUSTED` (as `CAPACITY`) from the server create nothing, and neither does any failure of the read-only image lookup. `ALREADY_EXISTS`, other statuses and lost responses stay unknown, and so does a refused sandbox after an OCI image was built, because the image remains.

## Snapshots

`box.snapshot()` captures the running sandbox's root filesystem with Modal's [filesystem snapshot](https://modal.com/docs/guide/sandbox-snapshots) (`Sandbox.snapshotFilesystem()`), which returns a new `im-` image. The snapshot reference's native ID is that image ID. Capture preserves files only: processes and memory are not saved, and a restore starts fresh. Modal does not document whether capture pauses the source, so the adapter reports a possible `pause`; the source keeps running afterwards. Requiring `filesystem+memory`, `maxInterruption: "none"` or a custom `cleanupAfterSeconds` rejects before any call. Setup accepts `snapshots: { preserve: Preserve.FILESYSTEM }`, which is the default; `Preserve.FILESYSTEM_AND_MEMORY` rejects at connect with `UNSUPPORTED`, before any Modal call. Modal's memory snapshots (alpha) and directory snapshots are not exposed.

Snapshot images keep Modal's default retention: Modal deletes them 30 days after capture, whether or not they were used. `retention.minimumSeconds` up to 30 days is accepted; longer rejects. `snapshot.restore()` creates a new sandbox from the image with the adapter's configured size, lifetime and region, `blocked` networking and no mounts, using the same named, tagged create and recovery as `sandboxes.create()`. `snapshots.get()` and `inspect()` confirm the image still exists; Modal reports no source, creation time or state for an image, so a reopened handle has none. `snapshot.delete()` deletes the image. Like Modal's own image delete, it cannot check whether a sandbox still uses the image, and deletion is irreversible.

`snapshots.list()` is unsupported because Modal has no API to list snapshots: save the reference returned by `snapshot()`. The pinned SDK sends the capture as one task-router request with a fresh snapshot ID and resends that same request only after a deadline or cancellation status. A lost capture response leaves no image ID to observe, so it is reported unknown and never replayed; any image it made expires with the 30-day retention. A definitive server refusal (as listed for create) or a failed source lookup rejects. A lost delete response is observed by checking whether the image still exists. Snapshot support has deterministic fixture coverage only and has not been run against the live Modal service.

The pinned SDK automatically retries task-router `execStart` and its filesystem write helper after transient errors. Sandbar sends `TaskExecStart` and stdin writes through a narrow gRPC wire client without hidden mutation retries. The execution ID is a deterministic UUID derived from the original submission ID, so SDK observation can reattach to that process without starting it again. Argv, shell, cwd, env, exit status, and binary stdout/stderr are supported with a combined 1 MiB output bound. Native exec timeouts constrain remote execution; abort and close stop local waits and transport calls, but do not promise remote process termination. After uncertain starts or writes, a missing process is unknown rather than proof of no effect.

Sustained processes (`box.processes.start({ output: { mode: "stream" } })` and `box.exec(input, { onOutput })`) start one `TaskExecStart` with a fresh execution ID and no native timeout, then stream `TaskExecStdioRead` chunks for stdout and stderr as they arrive, as text or exact bytes, with exit from `TaskExecWait`. Piped stdin uses offset-exact `TaskExecStdinWrite` calls; closed stdin sends EOF at once. The command router has no kill call, so the command runs through `/bin/sh -c 'echo $$ >"$0" && exec "$@"'`, which records its PID in `/tmp/.sandbar-process-<exec id>.pid` and then replaces itself with the command. `signal()` (SIGTERM, SIGKILL) and `terminate()` run `kill` against that PID in a second exec; they reach the launched process, not its descendants, and the PID file is left in `/tmp`. The image needs `/bin/sh`, `cat`, `kill` and a writable `/tmp`. `detach()` stops local reads and leaves the command running. Terminals and process reopening are unsupported.

Ordinary `box.exec` accepts finite stdin up to 1 MiB, with UTF-8 strings encoded by the SDK and exact bytes preserved. Modal starts the command once, writes the bytes at the router's required offsets, then acknowledges EOF; omitted input sends empty input and EOF. The adapter records whether full input-and-EOF delivery was acknowledged. A lost start, chunk or EOF acknowledgement stays unknown even if result observation later finds a completed command; observation never infers delivery from exit and never resends bytes. A result can recover after a lost result response only once input and EOF were fully acknowledged. This support is deterministic and packed evidence; no live Modal calls, paid builds or sandboxes have been run for finite input.

File reads use the pinned SDK's read-only filesystem tool with a 1 MiB transfer cap. File writes stream raw bytes to a sandbox-side POSIX shell command and verify the original process's exit code and byte-count output. `overwrite:false` uses shell noclobber (`O_EXCL` for an absent regular target), so a concurrent writer cannot be overwritten; an already present target is rejected before submission. `overwrite:true` replaces the target. The sandbox image must provide `/bin/sh`, `cat`, `mkdir`, and `wc`. The standard `python:3.12-slim` image has these tools; arbitrary prepared images should be checked by their owner. A crash or lost response while stdin is incomplete can leave a partial file or a waiting process; observation never replays bytes. A successful write is confirmed only by the same process's exit and byte count. No live Modal calls, paid builds or sandboxes have been run for qualification.

The task-router API and protobuf messages are private Modal interfaces. `createSdkTransport` checks the exact SDK version and official control endpoint; a Modal upgrade requires a wire audit. Local gRPC fixtures exercise one outbound start after a lost response, binary output and stdin offsets, truncation, abort/close, and observation by the original execution ID. Public SDK fixtures cover create, exec and write recovery across a reopened connection. Packed strict-TypeScript and Node/Bun consumers cover the separately installed package and direct fixture flow. These fixtures do not certify the real Modal service or every prepared image.

Modal's control-plane retry middleware performs three automatic retries by default even if the documented constructor `maxRetries:0` is passed. This package's public `grpcMiddleware` forwards `retries:0` to the built-in middleware. A local fake gRPC fixture demonstrated four outbound create attempts with only `maxRetries:0`, and one each for guarded App lookup, sandbox create, image build, and terminate calls. Ambiguous responses never trigger automatic mutation replay. Create recovery may discover an **active** sandbox by its unique native name and matching submission/operation tags. Destroy recovery polls the original native ID after a scope-checked submission and confirms success only when Modal reports it stopped; missing or running stays unknown. Absence is not proof of no effect, and expired or terminated sandboxes may be unobservable.

## Opt-in live check

`bun run --cwd packages/providers/modal test:live` is deliberately gated by `SANDBAR_MODAL_LIVE=1` and `SANDBAR_MODAL_BUDGET_ACK="one sandbox, at most 300 seconds"`. It also requires `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET`, `SANDBAR_MODAL_APP`, `SANDBAR_MODAL_ENVIRONMENT`, `SANDBAR_MODAL_REGION`, and `SANDBAR_MODAL_IMAGE_ID`. It creates at most one sandbox, sets a 300-second native timeout and attempts termination in `finally`. A failed create may have had an effect even if no handle was returned; preserve the emitted recovery reference and inspect Modal before any new run. The harness cannot enforce a dollar ceiling, so configure a provider-side spend alert or limit separately. This check has **not** been run; it requires separate live-use authorization and real credentials.

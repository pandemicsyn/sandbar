# Proposed live qualification — not authorized or run

Use Bun 1.3.14, the committed `vercel-profile.ts`, a borrowed existing team/project, universal managed image, `iad1`, two vCPUs, native deny policy and 300-second native session lifetime. Record exact commit, published boundary audit 3.6.1, Bun/platform, JUnit and private context. Keep the existing owner-only persistent ledger; unresolved Vercel custody blocks admission. No live keys or raw resource IDs belong in Git.

Run stages separately, serially, with no creator retry. Each fixture has setup 30s, exercise at most 120s and independent cleanup 60s plus client close. These are upper bounds, not a cost quote; approval must cover metered compute and residual snapshot storage until deletion. No custom images, builds, drives, mounted storage, publication or deployment.

1. Baseline `live/sandbox.test.ts`, supported cases only: one total/peak compute; zero snapshots/volumes/previews. Lifecycle/inventory, binary argv/shell/stdin, files/directories/streams, additive renewal and fresh-process sandbox reopen. This exercises at most two-vCPU × five-minute native lifetime (10 vCPU-minutes) plus native memory billing. Stop only the original immutable session; record retained named metadata.
2. `live/snapshots.test.ts`: three total compute, peak two; one snapshot; zero volumes/builds/previews. Filesystem capture terminates source; restore fresh independent compute, mutate first restore, inspect/reopen saved artifact in a separate process, tear down original compute, reconnect/restore original bytes again, independently delete snapshot. At most 30 vCPU-minutes under native TTL; snapshot storage persists until verified deletion and may outlive the run on lost ACK. No source replacement or memory-preservation assertion.
3. Process/PTY suites: one total/peak compute per selected fixture, zero snapshots/volumes/builds/previews. Select `live/interactive-processes.test.ts` and `live/process-extensions.test.ts`, now enabled for the Vercel profile; verify retained child, original-byte frames, bounded queues, EOF, disconnect/reopen gap, PTY dimensions and signals. Budget one five-minute/two-vCPU session (10 vCPU-minutes) for each explicitly selected fixture. List exact cases in approval before running, rather than enabling the full live directory.
4. Optional public preview: separately authorize one compute with exactly port 3000 public, no storage/builds. Existing profile exposes no ports, so use a reviewed saved-routing extension before this run. Verify public access, original identity/expiry, readiness separately and teardown. Bound is another 10 vCPU-minutes. Strict network isolation requires its own matched control/probe plan; baseline deny policy is not an isolation pass.

Baseline plus snapshots alone: four total compute, peak two, one retained snapshot, no drives/builds/previews; maximum 40 vCPU-minutes if every session reaches native TTL. Run admission remains serial. Process/preview allocation is additional only if explicitly selected and approved.

Before effects, the ordinary SDK ledger saves scoped attempt identities. After ACK it saves original session/command/artifact IDs. On failure, stop and confirm each owned original session, delete only the exact acknowledged snapshot, and close clients. Never delete named metadata or adopt by source/name. Lost snapshot ACK can leave an unresolved billed artifact: preserve source attempt/custody and investigate manually; a unique source match alone is not operation ownership. Do not silently allocate another snapshot or clear custody. Native TTL stops compute only and is not snapshot cleanup.

After interruption, verify the prior process has stopped and use `live/reconcile.ts` with the same ledger, run UUID, current credentials and saved profile/routing. Observe previous attempts without replay; uncertain deletes get GET evidence, never a second DELETE. Unresolved creators/artifacts remain unresolved. Import only actual JUnit results with cleanup/close context, review sanitized evidence, then render support pages. All current live records remain not-run.

Persistent mode is implemented and fixture-tested separately from the committed disposable live profile. A future persistent live run must use a reviewed profile with `persistent:true`, explicitly select `lifecycle-suspend-resume` (`SANDBAR_VERCEL_PERSISTENT=true`), budget two VM sessions plus rolling automatic snapshot storage, and extend durable storage custody/cleanup before admission. The shared lifecycle assertion verifies terminated processes and a fresh VM while saved file bytes and logical reference survive. Current live runner cleanup must not certify persistent storage cleanup merely from compute deletion. This is an outstanding live validation/runner gate; no persistent live run is authorized by this proposal.

# sandbar-adapter

The public authoring API for Sandbar adapters. Install with `npm install sandbar-adapter` and import `defineAdapter` from `sandbar-adapter`. The `sandbar-adapter/testing` subpath contains the conformance suite for adapter authors.

See the [adapter guide](https://sandbarsdk.dev/docs/guides/write-an-adapter/) for supported capabilities, validation, and recovery behavior. This package does not require a Sandbar service.

State portability foundations add `ResourceReference`, `SnapshotRequest`, `SnapshotProfile`, `Support<T>`, and pure profile resolution. A minimal create/destroy adapter remains valid. Optional `snapshotProfiles(target, context)` supplies read-only evidence for the checked create class or sandbox. It must return unknown when that evidence needs a paid build or probe, and unavailable when access/configuration/current state prevents support. Capture is reported supported only when a `snapshotCapture` handler is also installed. The SDK exposes capture submission, scoped snapshot and volume handles, independently supported artifact inventory/deletion and create-time mounts through optional adapter handlers. Do not advertise native functionality that the adapter has not implemented and qualified.

Profiles bind exact preservation to interruption, final source lifecycle, consistency, valid source states, connection handling, mount exclusions, and known minimum retention. They cannot be combined to fabricate a supported request. Missing retention cannot satisfy a positive minimum. Read hooks and mutation preparation never allocate or stop compute. Existing recovery attempts retain their sandbox field; the generic resource constraint now accepts scoped references and capture plans, resources and mounts for artifact operations. State mutation kinds retain durable pre-submit references and application-owned provider custody checkpoints. Recovery remains observation-only and never replays a capture, restore or deletion.

A continuation may return `ctx.reject()` to confirm a durable stage proven never dispatched. Read-only observation cannot certify rejection. The built-ins persist an explicit rejected checkpoint when E2B capture/restore or E2B/Daytona volume creation is cancelled before dispatch; recovery observation directs the caller to `continue()`, which confirms the no-effect rejection without provider I/O. Uncertain dispatch remains unknown and cannot replay.

E2B snapshot deletion requires a private containing template with exactly one native build. Application-retained history cannot authorize deleting unrelated generations in a multi-build template; delete such templates through the provider’s own management API when intended.

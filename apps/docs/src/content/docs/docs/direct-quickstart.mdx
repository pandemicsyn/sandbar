Run a command in a sandbox from your own TypeScript application. You'll need a provider account and **Bun** to run this example. The SDK also supports server-side [Node.js](/docs/providers/support/#runtimes).

## 1. Set up a checkout

Sandbar packages are not published yet. Use **Bun 1.3.14** and run from a source checkout:

```sh
git clone https://github.com/pandemicsyn/sandbar.git
cd sandbar
bun install --frozen-lockfile
bun run build:packages
```

Already in a checkout? Run the install and build commands from its root. The workspace resolves `sandbar-sdk`, the official `sandbar-daytona` and `sandbar-e2b` adapters, and experimental `sandbar-modal` locally. Once published, install `sandbar-sdk sandbar-daytona` or `sandbar-sdk sandbar-e2b` in your application. Modal has offline coverage and has not been live-qualified; [compare provider support](/docs/providers/support/).

To run OpenCode rather than a shell command, use the [runnable agent examples](/docs/guides/runnable-agent-examples/).

## 2. Add your credentials

Create an untracked `.env.local` file in the repository root:

Add `.env.local` to your `.gitignore`. Keep credentials on the server and out of browser code. Running the example creates a sandbox in your provider account and may incur usage charges.

You should see `Hello from Sandbar!`. The Daytona and E2B examples use `sandboxes.with()` to clean up the sandbox after the callback succeeds or throws. An outer `finally` closes the client. The experimental Modal example shows manual sandbox cleanup. `close()` alone does **not** destroy compute. If creation or cleanup has an uncertain outcome, follow [Errors and recovery](/docs/guides/recovery/) before retrying.

For temporary work, prefer [scoped sandbox cleanup](/docs/guides/resources/#create-and-clean-up). The scope retains snapshots and volumes, and cleanup failures preserve the callback result or error plus recovery information. Use manual `create()` when the sandbox should outlive the callback.

## Bound connection waits

`Sandbar.connect(adapter, { signal, timeoutMs: 30_000 })` accepts `ConnectOptions`.
The advanced definition/config/credentials form accepts the same controls in its options object.
`await client.close({ signal: cleanupSignal, timeoutMs: 5_000 })` accepts `CloseOptions`.
Only positive finite safe-integer budgets are accepted; longer budgets are allowed.

**Compatibility change:** setup now defaults to a 30-second local wait and each close call defaults to a 5-second local wait. These budgets do not change sandbox lifetime, command deadlines or remote compute. Setup cancellation reports `WAIT_ABORTED`; expiry reports `TIMEOUT`, with effect `none`, cause and a phase-specific message. Aborting the setup signal after the client returns has no effect on the usable client.

Close immediately prevents new work and starts local cleanup once. Cancelling or timing out one close wait leaves that attempt running; a later close can wait for it. Cleanup runs in reverse registration order. A hanging hook can leave later hooks pending; failed releases are sent to `onDiagnostic` and remaining cleanup continues. Successful close means registered cleanup was attempted, not that every failed release succeeded. Late resources from abandoned setup are released locally. Neither setup failure nor close deletes sandboxes, volumes or snapshots; use explicit resource operations for those actions.

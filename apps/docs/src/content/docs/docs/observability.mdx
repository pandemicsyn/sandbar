Sandbar uses OpenTelemetry to record spans: timed records of SDK calls and their outcomes. When you call the SDK inside an active request or job span, its spans appear as children of that span. Your application sets up tracing, chooses which traces to sample, exports them and shuts tracing down. Importing Sandbar does not set up telemetry.

## Already using telemetry

### OpenTelemetry

Keep your existing OpenTelemetry setup. Sandbar uses its provider and active context without an extra tracing option. Initialize telemetry before application work, then call the SDK inside your request or job span:

```ts
import { Sandbar } from "sandbar-sdk";
import { daytona } from "@sandbar-sdk/daytona";

const client = await Sandbar.connect(
  daytona({
    apiKey: process.env.DAYTONA_API_KEY!,
    target: process.env.DAYTONA_TARGET ?? "us",
  }),
);
// Use client inside your existing active request/job span.
await client.close();
```

### Sentry

If Sentry manages your application's tracing, add `enableOpenTelemetrySetup: true` to your existing `Sentry.init()` configuration. Keep your current DSN, sampling, integrations, error hooks and shutdown. This enables Sentry's OpenTelemetry bridge, so Sandbar spans join Sentry's active trace without a second provider or exporter. This setup is tested with Sentry 11.1.0 on Node and Bun.

If your application already owns an OpenTelemetry provider, keep that provider instead. Add `Sentry.openTelemetryIntegration()` to your existing Sentry integrations, set `enableOpenTelemetrySetup: false`, and leave Sentry's `tracesSampleRate`/`tracesSampler` unset. Your OTel sampler remains in control. To send spans to Sentry, add an OTLP exporter using `Sentry.getOtlpTracesEndpoint(dsn)` to that provider. [Sentry's custom-pipeline guide](https://docs.sentry.io/platforms/javascript/guides/node/opentelemetry/custom-setup/) covers that existing-provider configuration.

### Datadog

For Node applications already running `dd-trace`, register its OpenTelemetry bridge once during your existing startup, before importing application modules. Keep the existing Datadog initialization, plugins, sampling and Agent configuration:

```ts
import tracer from "dd-trace";

// Your application's tracer.init(...) already ran.
const provider = new tracer.TracerProvider();
provider.register();
```

Sandbar spans now join the active Datadog request/job trace. Do not register another OTel SDK provider on this path. The bridge is tested with `dd-trace` 6.17.0 on Node 22. [Datadog's API bridge instructions](https://docs.datadoghq.com/opentelemetry/instrument/dd_sdks/api_support/) describe startup and custom instrumentation.

For Bun, or an application already exporting OTel to Datadog, keep the OTel provider and use an Agent/Collector OTLP endpoint. The complete OTLP example below works on both runtimes.

## Starting fresh

A usable Sandbar release has not been published yet. Registry versions `0.0.0` are name-reservation placeholders. The installation commands below are for a future release; for now, use the [repository setup and example commands](/docs/direct-quickstart/) with workspace packages.

## Optional issue capture and privacy

Sandbar records span status but does not create Sentry issues automatically. To report an SDK failure, use `diagnosticContext(error)` to collect a small set of safe fields. Avoid sending the original error, its cause or command output, which may contain private data. This example limits its event processor to one explicit capture and keeps your global `beforeSend` and default integrations:

Call it once inside your request or job's catch block. The processor builds a new event containing only the allowed diagnostic and trace fields. Unrelated application errors keep their normal messages, exceptions, stacks and tags. Your other event processors and `beforeSend` still apply. Vendor instrumentation, HTTP instrumentation and your own spans may collect more data than Sandbar does; configure their privacy settings separately.

## Tracing controls

No option is needed to use the application's provider. `tracing: false` disables SDK spans for one client:

```ts
import { Sandbar } from "sandbar-sdk";
import { daytona } from "@sandbar-sdk/daytona";

const client = await Sandbar.connect(
  daytona({
    apiKey: process.env.DAYTONA_API_KEY!,
    target: "us",
  }),
  { tracing: false },
);
await client.close();
```

To supply a provider directly, use `tracing: { tracerProvider }`. You must still configure a compatible async context manager to connect spans across asynchronous calls. A shared client reads the active context separately for each call. `client.close()` releases SDK resources; your application must flush and shut down its tracing provider. Disabling SDK tracing does not disable other instrumentation.

## Interpret spans and errors

SDK span names are fixed and use OpenTelemetry's `INTERNAL` kind. They cover connection, support queries, inventory, sandbox listing, sandbox creation, image builds, execution, files, previews, processes, terminals, inspection, destruction, operation observation/recovery and client close.

The work inside an operation appears as `sandbar.prepare`, `sandbar.submit` and `sandbar.wait`. Explicit advanced observation uses `sandbar.observe`. Convenience calls avoid duplicate spans for their internal public submit/wait methods. Waiting records a poll count and at most eight state-change events; it does not create a span for every unchanged poll.

Two attributes answer different questions:

- `sandbar.call.outcome`: did this SDK call succeed, fail or get cancelled? Values are `success`, `error` and `cancelled`.
- `sandbar.effect`: what is known about changes made by the operation? Values are `none`, `possible`, `applied`, `partial` and `unknown`.

A successful observation can report that remote work is still pending or its outcome is unknown. A query can successfully report unsupported behavior. A nonzero `exec()` exit throws `NonzeroExitError`; its span records the exit code and `applied` effect because the command ran, even though the SDK call failed.

Cancelling local waiting after submission does not prove that remote work stopped. If a submission response is lost, use observation and recovery to check the original operation instead of submitting it again.

```ts
import { diagnosticContext } from "sandbar-sdk";

try {
  // await your Sandbar operation
} catch (error) {
  const diagnostic = diagnosticContext(error);
  // Pass this bounded record to your application's issue/reporting system.
  // Keep the original error/handle if recovery is needed.
}
```

`diagnosticContext` returns an allowed error code and effect, safe Sandbar operation/submission IDs when known, the known operation state and `recoveryAvailable`. State can be `pending`, `completed`, `rejected`, `failed` or `unknown`. The helper reads only local data and does no I/O.

`recoveryAvailable` is true only for immutable references already validated by the SDK. A reference loaded from storage is unverified until `recover()` returns a handle. Diagnostics do not inspect its opaque token and cannot be used to recover an operation themselves. Keep the original error or handle when recovery is needed.

SDK diagnostics omit invocation keys, native resource identifiers, scope, recovery tokens, URLs and raw error messages or causes. Unknown provider labels become `custom`. SDK spans omit commands, arguments, environment values, paths, file contents, stdout/stderr, image names, credentials and URLs by default.

## Recovery and HTTP instrumentation

An operation handle may retain a validated trace context so later spans can link back to the original call. Saved recovery references do not carry that context. After restarting the client, recover inside the current request or job span and use the safe operation ID to correlate work when the original trace is unavailable. Recovery still works when traces are missing or unsampled. A trace link does not guarantee that a vendor displays the work as one continuous tree.

Sandbar does not add HTTP transport spans, patch global `fetch`, or send tracing headers to providers or guest services. Your application's HTTP instrumentation can add its own spans and headers.

Local tests use real `instrumentation-http` and verify one `CLIENT` child span for one adapter file-read request on Node and Bun's compatible `http.request`. They do **not** verify automatic tracing of Bun's native `fetch`.

For production HTTP instrumentation, ignore provider and guest destinations by default, send trace headers only to trusted destinations, and remove private URL, query and header data before export. Sandbar's safe fields cannot scrub data collected by other HTTP instrumentation, native SDKs, application spans or vendor captures.

## Qualification and debugging

From a source checkout, run `bun run build:packages`, then `bun run observability:check`. This guide displays the same example files that documentation checks compile and local tracing tests execute. The tests replace provider and vendor endpoints with local stand-ins; they make no live provider calls.

The examples and tests live in `packages/sdk-qualification/observability`. They cover Node 22.23.3 and Bun 1.3.14 independently, including local export, sanitized issues, sampling, concurrent parent spans and shutdown deadlines. They do not qualify metrics, structured logs, vendor UI or live provider telemetry. Native Datadog tests cover Node; Bun uses OTLP.

If spans are missing, check that tracing is enabled, telemetry was initialized before application work, and Sandbar shares the application's `@opentelemetry/api` instance. Also check that sampling selected the trace and the exporter finished before its deadline.

If spans are disconnected, check the async context manager and make each call inside the intended request or job span. Supplying a provider does not install a context manager. You can still correlate recovery by operation ID when traces are absent or unsampled.
